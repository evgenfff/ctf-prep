# 05. Финал Attack-Defense: playbook

Финал — это не «ещё один jeopardy». Здесь нельзя решить 5 задач и уйти. Нужно **непрерывно** защищать сервисы, успевать патчить и снимать чужие флаги. Ошибка в патче может стоить больше, чем невзятый эксплойт.

Даты 2026: **04.12** — школьный/СПО (финал 2.5), **05.12** — академический/смешанный (полуфинал 2.0), **06.12** — секретный финал 3.0.

---

## 1. Чем AD отличается от отбора

| | Отбор (jeopardy) | Финал (AD) |
|---|---|---|
| Время | 24 часа, можно спать | 8 часов, непрерывно (день 09:00–19:30) |
| Результат | флаги за задачи | флаги за атаку + защита + SLA |
| Работа | можно менять тему | нельзя бросить сервис |
| Риск | потерять очки | сломать сервис и потерять больше |
| Команда | 5–7, каждый сам | 5–7, нужны роли и дежурства |
| Инфраструктура | чужая платформа | ваши ВМ и ваши патчи |

**Главный принцип:** сначала стабильность, потом атака. Сервис, который упал, не приносит очков ни за защиту, ни за атаку.

---

## 2. Формат 2025 (ориентир для 2026)

- 4 сервиса, каждый на отдельной ВМ: **4 CPU / 4 GB RAM**.
- Сервисы запущены в **k3s**.
- Время: день 09:00–19:30, игровое окно 10:00–18:00 (8 часов); в 2025 было 10:00–19:00 (9 часов).
- Чекеры проверяют функциональность и флаги.
- Флаги выдаются чекером и живут ограниченное время.
- За защиту начисляются очки, если сервис отвечает и флаги не украдены.
- За атаку — очки за валидные чужие флаги.
- SLA: если сервис недоступен, очки за защиту сгорают, иногда с штрафом.

**Что уточнить перед финалом:**
- точная формула очков (атака/защита/SLA);
- сколько живёт флаг и как часто чекер его обновляет;
- что считается «сервис доступен»;
- можно ли перезапускать поды и менять код;
- есть ли ограничения на патчи (например, нельзя менять API);
- как передаются флаги (формат, endpoint);
- есть ли штраф за падение.

## 3. Роли на финал

### Минимальный состав (5 человек)
| Роль | Ответственность |
|---|---|
| Капитан / координатор | таймлайн, связь, распределение, решение о патчах |
| Service owner ×2 | каждый ведёт 2 сервиса: аудит, патч, восстановление |
| Attacker ×2 | эксплойты, ферма флагов, разведка чужих сервисов |
| Defender / infra | мониторинг, логи, бэкапы, перезапуск, проверка checker |

### Полный состав (7 человек)
- 1 капитан;
- 4 service owner (по одному на сервис);
- 2 attacker;
- 1 defender/infra (может быть капитаном).

**Правило:** service owner не уходит в атаку, пока его сервис не стабилен и не пропатчен. Attacker не трогает патчи, пока не согласует с owner.

## 4. Таймлайн 10:00–18:00 (день 09:00–19:30)

### T-60 минут
- Все на связи, доступы проверены.
- Снапшоты ВМ (если можно).
- Открыты: исходники, конфиги, логи, терминалы.
- Проверен checker: какой endpoint, какой формат флага.
- Капитан фиксирует план на первый час.

### 10:00–10:30 — «Стабилизация»
- Проверить, что все 4 сервиса живы.
- Прогнать checker вручную (если есть утилита).
- Сделать снапшот/бэкап конфигов.
- Прочитать README/исходники каждого сервиса.
- **Не патчить в первые 30 минут**, если нет критической уязвимости.

### 10:30–11:30 — «Аудит»
- Каждый owner проходит чек-лист (раздел 5).
- Attacker начинает разведку: какие endpoint'ы, какие роли, где флаги.
- Капитан собирает карту: сервис → вероятная уязвимость → приоритет.

### 11:30–13:00 — «Первые эксплойты»
- Attacker пишет эксплойт на самый вероятный сервис.
- Owner параллельно патчит самую опасную дыру.
- Проверка: патч не сломал checker.

### 13:00–14:00 — обед по очереди
- Сервисы не остаются без присмотра.
- Attacker продолжает ферму.

### 14:00–16:30 — «Основная игра»
- Цикл 15 минут: атака → проверка флагов → патч → мониторинг.
- Каждые 30 минут — короткий стендап.
- Ротация: owner отдыхает 15 минут, attacker продолжает.

### 16:30–17:30 — «Финишный рывок»
- Добить эксплойты, которые почти работают.
- Не начинать новые сложные атаки.
- Проверить, что все патчи стабильны.

### 17:30–18:00 — «Заморозка»
- Никаких новых патчей, если они не критичны.
- Проверить сервисы, логи, флаги.
- Записать результаты.

## 5. Аудит сервиса: чек-лист за 30 минут

### 5.1. Инвентаризация
- [ ] Язык, фреймворк, версия.
- [ ] Все маршруты/эндпоинты.
- [ ] Роли и аутентификация.
- [ ] Где хранятся флаги (БД, файлы, S3, env).
- [ ] Внешние зависимости и их версии.
- [ ] Конфиги и секреты в репозитории.
- [ ] Логи и метрики.

### 5.2. Типовые уязвимости
| Класс | Что искать | Быстрая проверка |
|---|---|---|
| IDOR | объект по ID без проверки владельца | подставить чужой ID |
| Broken auth | роль в токене/заголовке | изменить `role`, `user_id` |
| SQLi | конкатенация запросов | `'`, `"`, `1 OR 1=1` |
| NoSQLi | операторы в JSON | `{"$ne": null}`, `{"$regex": ".*"}` |
| SSRF | URL из пользователя | `http://127.0.0.1`, `file://` |
| Path traversal | имя файла | `../../etc/passwd` |
| Command injection | shell от пользователя | `; id`, `$(id)` |
| Deserialization | pickle/boost/Java | подмена объекта |
| JWT | alg/none, kid, jwk | декодировать, менять |
| Race | баланс/купон/лайк | параллельные запросы |
| Crypto | предсказуемый ID/токен | UUIDv1, time-based |
| Secrets | пароли в коде/конфиге | grep |

### 5.3. Команды
```bash
# маршруты
grep -RInE "router\.|app\.(get|post|put|delete)|@app\.(route|get|post)|HandleFunc|http\.Handle" .
# секреты
grep -RInE "password|secret|token|api[_-]?key|BEGIN (RSA|OPENSSH)" . --exclude-dir=.git
# зависимости
cat go.mod package.json requirements.txt Cargo.toml 2>/dev/null
# Docker/k8s
find . -name "Dockerfile" -o -name "*.yaml" -o -name "*.yml" | head -50
# логи
kubectl get pods; kubectl logs <pod> --tail=100
```

## 6. Эксплуатация: что делать в первые часы

### 6.1. Приоритеты
1. **Уязвимость, которая даёт флаги напрямую** (IDOR, чтение БД, S3).
2. **Уязвимость, которая даёт RCE** (десериализация, command injection).
3. **Уязвимость, которая даёт доступ к внутренним сервисам** (SSRF).
4. **Уязвимость, которая ломает checker** (не эксплуатировать, если это саботаж).

### 6.2. Шаблон эксплойта
```python
import requests, re, sys, time
from concurrent.futures import ThreadPoolExecutor

BASE = "http://<ip>:<port>"
FLAG_RE = re.compile(r"[A-Za-z0-9_]+\{[^}]+\}")

def attack(target):
    try:
        r = requests.get(f"{BASE}/...", params={"id": target}, timeout=5)
        m = FLAG_RE.search(r.text)
        if m:
            return m.group(0)
    except Exception as e:
        pass
    return None

def main():
    targets = range(1, 1000)
    with ThreadPoolExecutor(max_workers=20) as ex:
        for flag in ex.map(attack, targets):
            if flag:
                print(flag, flush=True)
                # submit(flag)

if __name__ == "__main__":
    main()
```

**Правила:**
- Таймаут 3–5 секунд, иначе ферма зависнет.
- 10–20 потоков, не 200: иначе положите сервис и потеряете SLA.
- Логировать каждый успешный флаг и каждую ошибку.
- Не долбить один endpoint, если он отвечает 500.
- Проверять формат флага перед отправкой.

### 6.3. Разведка чужих сервисов
- Те же сервисы у всех команд, но данные разные.
- Сначала определите, какой сервис самый «дырявый» по вашей экспертизе.
- Не тратьте 3 часа на один сервис, если есть 3 других.
- Используйте `attack_data`/`checker` из репозитория, чтобы понять, где лежат флаги.

## 7. Защита: как патчить и не сломать

### 7.1. Правила
1. **Сначала бэкап.** `cp -r` или git-ветка. Без бэкапа не патчить.
2. **Минимальный патч.** Меняйте только уязвимую проверку, не переписывайте архитектуру.
3. **Не меняйте API.** Checker ходит по тем же endpoint'ам; если вы удалите функцию, потеряете SLA.
4. **Тестируйте локально.** Поднимите копию, прогоните checker/ручные запросы.
5. **Один патч — один сервис.** Не катить всё сразу.
6. **Логируйте.** После патча проверьте, что сервис отвечает и флаги не текут.
7. **Откат.** Держите команду отката наготове.

### 7.2. Патчи для типовых дыр
| Дыра | Патч |
|---|---|
| IDOR | проверять `user_id` объекта == текущий пользователь |
| Роль в токене | подписывать токен, не доверять полю `role` |
| SQLi | параметризованные запросы |
| NoSQLi | валидировать типы, запретить `$`-операторы |
| SSRF | allowlist доменов, запрет `file://`, `127.0.0.1`, metadata |
| Path traversal | `filepath.Clean`, проверка префикса |
| Command injection | не передавать ввод в shell, использовать argv |
| Deserialization | подписывать/валидировать, не десериализовать пользовательский ввод |
| JWT | фиксировать alg, проверять подпись и `kid` |
| UUIDv1 | заменить на криптостойкий random |
| Секреты | вынести в env/секреты, ротировать |

### 7.3. Патч в k3s (пример из warehouse 2025)
```bash
cd /service/<service>
sudo docker build -f utils/docker/<service>.Dockerfile -t <service>-<name>:latest .
kubectl delete pod <pod-name>
sleep 10
kubectl get pods
```
Если образ с тегом `latest`, новый под подхватит его автоматически.

**Важно:** перед пересборкой проверьте, что Dockerfile и контекст не тянут лишнее; сборка может занять минуты. Держите старый образ для отката.

### 7.4. Что не делать
- Не удалять эндпоинты, которые вызывает checker.
- Не менять формат ответа.
- Не ставить `return 403` на всё.
- Не перезапускать всё одновременно.
- Не патчить «на глаз» без теста.
- Не отключать логи в момент атаки.

## 8. Разбор сервисов 2025

### 8.1. Veladora (Go/Gin)

**Сценарий:** бар, заказ напитков, оплата, диалог с барменом, восстановление диалога по 32-байтному значению.

**Уязвимость 1 — инъекция в диалог произвольного пользователя.**
При отправке сообщения можно указать `username`, и сервер не проверяет, что это текущий пользователь:
```go
if req.Username != "" {
    var resolvedUserID int
    database.DB.QueryRow(ctx, "SELECT id FROM users WHERE username = $1", req.Username).Scan(&resolvedUserID)
    conversationOwnerID = resolvedUserID
}
```
**Эксплуатация:** внедрить свою 32-байтную константу в диалог жертвы, затем восстановить диалог по этой константе и получить флаг.
**Фикс:** проверять, что `req.Username` совпадает с авторизованным пользователем, либо вообще не принимать username от клиента.

**Уязвимость 2 — IDOR + предсказуемый payment ID.**
ID чека генерируется функцией, где используется `RANDOM()` и XOR с одним байтом `vt`; структура предсказуема:
```
<hex(lower(username) XOR vt)>_<hex(bill_id XOR vt)>_<hex(vt)>
```
Плюс при доступе к чеку нет проверки владельца.
**Эксплуатация:** перебрать 16 вариантов `vt` и ID счёта, получить чужой оплаченный чек с флагом.
**Фикс:** криптостойкий random ID + проверка `bill.user_id == current_user`.

**Урок:** в AD-сервисах часто две независимые дыры; одна даёт флаг напрямую, другая — доступ к данным. Патчить надо обе.

---

### 8.2. Archive (C++/boost)

**Сценарий:** загрузка библиотеки SQLite с книгами (сериализованные объекты), просмотр книг, смена библиотеки.

**Уязвимость:** CVE-2023-34399 в boost serialization. Книги сериализуются как указатель и десериализуются так же. Можно передать кастомную строку с отрицательным индексом:
```
22 serialization::archive 18 -3083 1 1
0 3 kek 3 pek 1777
```
Отрицательный индекс позволяет манипулировать объектом, который берётся из массива.
**Эксплуатация:** heap feng shui → контролируемый объект → чтение/выполнение.
**Фикс:** бинарный патч проверки индекса (индекс < 0 → отказ) или переписать на безопасном языке.
**Урок:** если в сервисе есть десериализация — это первый кандидат на атаку. CVE ищется по версии зависимости за 5 минут.

---

### 8.3. Warehouse (Go, 4 микросервиса)

**Сценарий:** регистрация, склад-реалм, позиции, роли, обратный прокси с TI-фидами.

**Уязвимость 1 — UUIDv1 как API key.**
В `ti-server` API-ключ приватного фида генерируется через `uuid.NewUUID()` (UUIDv1). Первая часть зависит от времени, вторая статична для хоста. Зная ID фида (создан примерно в то же время), можно перебрать ключ за 5–7 итераций. Ключ хешируется: `md5(UUIDv1)`.
**Эксплуатация:** получить ID приватного фида → брутфорс временной части → доступ к индикаторам/флагам.
**Фикс:** `crypto/rand` + base64 (пример в writeup) или патч SQL-функции `hash` в БД.

**Уязвимость 2 — SSRF в gateway-server.**
`auth-server` на `/users/search?query=` возвращает email (флаг), но защищён middleware `InternalOnly`, которая требует заголовок `X-Forwarded-Host`. `gateway-server` при проксировании **затирает все заголовки**, кроме `Authorization`, включая `X-Forwarded-Host`. Создаём virtual service с внутренним адресом `http://warehouse-auth-server:8081` и идём через gateway на `/users/search`.
**Эксплуатация:** создать gateway → направить на auth-server → вытащить email/флаг.
**Фикс:** не затирать `X-Forwarded-Host` слепо; проверять источник; закрыть `/users/search` на уровне сети; не отдавать email.

**Урок:** микросервисы — это цепочки доверия. Одна middleware считает заголовок доверенным, другая его удаляет. Ищите несоответствия.

### 8.4. Prototype (Python/Flask/MinIO)

**Сценарий:** создание коктейлей, рецепты, лайки, превью-картинки, секретный ингредиент.

**Архитектура:** LB → Nginx → Gunicorn/Flask ×4 → MinIO; часть ФС контейнера смонтирована через CSI-драйвер MinIO.

**Уязвимость:** CVE-2025-62506 в `minio/minio:latest`. `/obtain_account` возвращает `X-Token`; после base64 — `['access_key:secret_key', 'salt']`. Ключи выданы для service-account с ограниченными правами. Если создать новый service-account **без явных политик**, уязвимость повышает права до администратора. Далее найти бакет, который маппит ФС, и вычитать файлы с флагами/индексы пользователей.
**Сложность:** S3 требует корректной подписи; при запросах извне надо самостоятельно подписывать внутрикластерный путь `http://prototype-s3.default.svc.cluster.local:9000/`, обращаясь к внешнему `/s3`.
**Фикс:** заменить образ на фиксированный (`RELEASE.2025-10-15T17-29-55Z` или новее) либо закрыть `/admin` на nginx.

**Unintended:** утечка эффективного HMAC-ключа из-за переполнения SHA256 солью — выдавался ключ для подписи токена.

**Урок:** «latest» — это уязвимость. В AD всегда проверяйте версии образов и известные CVE. Иногда unintended проще авторского решения.

## 12. Типичные ошибки на AD

1. **Патчить всё сразу.** Ломаете checker и теряете SLA.
2. **Удалить эндпоинт.** Checker не может проверить — минус очки.
3. **Забыть про вторую уязвимость.** Патчите IDOR, а RCE остаётся.
4. **Ферма на 200 потоков.** Кладёте сервис и получаете бан.
5. **Не логировать флаги.** Не знаете, что уже сдали.
6. **Играть в один сервис.** Три других приносят больше.
7. **Не спать/не есть.** 8 часов без перерыва = ошибки.
8. **Менять API «для безопасности».** Ломаете совместимость.
9. **Игнорировать `latest`.** Известная CVE решается за 10 минут.
10. **Не делать бэкап.** Откат невозможен.

## 13. Как тренироваться до финала

1. **Поднять 2 сервиса из `ctfcup2025-ad` локально** (Docker/k3s).
2. **Пройти чек-лист аудита** на `veladora` и `warehouse`.
3. **Написать эксплойт** на IDOR Veladora и SSRF Warehouse.
4. **Сделать патч** и проверить, что функциональность жива.
5. **Прогнать checker** (в репозитории есть `checkers/`).
6. **Сыграть mock AD** 3 часа: 2 команды, 2 сервиса, счёт по флагам.

**Минимальная цель к 05.12:** уметь за 30 минут поднять сервис, найти IDOR/SSRF, написать эксплойт и накатить патч без падения.
